# Протокол 1.0

WebSocket `/bridge`, управляющие сообщения JSON. Сначала hello, затем authenticate. `session_id` возвращается hello и меняется при смене мира/игрока/измерения; старые команды нельзя переносить между сессиями.

```json
{
  "protocol_version": "1.0", "session_id": "ID from hello",
  "message_id": "unique delivery ID", "request_id": "unique command ID",
  "actor_id": "UUID from capabilities", "expected_revision": 42,
  "type": "task.submit",
  "data": {
    "action": "move.to", "parameters": {"target": {"x": 10, "y": 64, "z": 20}},
    "priority": 0, "timeout_ticks": 1200, "max_actions": 10000, "depends_on": []
  }
}
```

`expected_revision` опционален; для изменяющих действий обязателен actor_id. Первый hello допускает `session_id: null`; отправьте `data.actor_mode: existing_player`, затем authenticate с `data.token`. Каждое сообщение требует message_id, request_id и объект data. Не журналируйте аутентификационные сообщения.

Ответ: type=response, тот же request_id. Ошибка: type=error, data.code/message/retryable/revision. Длительное действие отвечает status=accepted и task_id; успех определяется терминальным состоянием.

В течение 10 минут (ёмкость 4096) повтор request_id с тем же типом/содержимым возвращает сохранённое подтверждение. Другие параметры дают request_id_conflict. Переполнение окна отклоняет новые запросы. После истечения окна изменяющую команду нельзя повторять без проверки мира.

## Сессия, наблюдение и задачи

| Операция | data |
| --- | --- |
| session.hello | actor_mode: existing_player |
| session.authenticate | token |
| session.capabilities / ping | {} |
| session.resume | after_sequence |
| observe.snapshot | опционально profile: full / compact |
| observe.subscribe | interval_ticks: 4..1200, events: true, опционально profile: full / compact |
| observe.unsubscribe | {} |
| task.submit | action, parameters, priority: -100..100, timeout_ticks: 1..12000, max_actions: 1..100000, depends_on: [task_id], опционально expected_control_epoch и model_goal_id |
| task.status / pause / resume / cancel | task_id |
| task.list / control.stop | {} |
| map.query / memory.query | x,y,z (конечные числа); block: точный namespace:id или blocks: до 16 точных ID; radius: 1..64, limit: 1..128, опционально max_age_ticks: 0..120000 |
| model.query | operation, arguments, expected_control_epoch, опционально model_goal_id |
| memory.annotate | text, опционально position |
| vision.capture / subscribe | width: 64..640, height: 64..360, interval_ticks: 4..1200, опционально crop и observation_profile: full / compact |
| vision.unsubscribe | {} |
| model.status | {} — текущая цель, статус и подключение контроллера |
| model.claim | goal_id — принять цель, созданную владельцем в окне F7 |
| model.report | goal_id, state: thinking / executing / completed / waiting / failed, step, detail |

Мод 0.7.0 сохраняет протокол 1.0. Capabilities объявляет `observation_profiles`, `decision_guards`, `model_control` и `queries`. `actions` отражает доступные адаптеру действия с учётом `allowedActions` владельца; `queries` перечисляет доступные операции чтения/планирования. На внешнем multiplayer-сервере управляемых действий нет. Профиль `full` по умолчанию сохраняет прежний снимок. `compact` возвращает шесть ближайших наблюдённых блоков, четыре ближайшие сущности, занятые слоты инвентаря и занятые слоты меню с первыми четырьмя пригодными пустыми слотами main/hotbar/container; номера слотов, UUID, свойства блоков и menu revision сохраняются. В `actor` указываются `main_hand` и `off_hand`; наблюдаемая предметная сущность `minecraft:item` включает `entity.item` с `type`, `count` и `damage`. Пропущенные данные остаются неизвестными.

`model.query` требует разрешения F8 и актуального `expected_control_epoch`; прямые запросы чтения требуют аутентификации и разрешённой операции, но не F8. `model.query` передаёт `{operation, arguments, expected_control_epoch, model_goal_id}`. Поддержанные операции: `map.nearest`, `map.query`, `memory.query`, `craft.plan`, `build.plan`, `route.plan`, `inventory.inspect` (для последней опционален `item`). Модель может выбрать `action: query`; запрос расходует один шаг решения модели, но не меняет игровой мир. Сначала запрашивайте `craft.plan` или `build.plan`, затем отправляйте отдельную задачу на исполнение. Существующие SDK read endpoints `map.query` и `memory.query` также остаются доступны напрямую.

Снимок содержит `control_epoch`. Контроллер сохраняет его до обращения к модели и передаёт как `task.submit.data.expected_control_epoch`. Мод проверяет значение при принятии задачи; ручной ввод, остановка, повторное разрешение управления или разрыв сессии делают старое решение недействительным (`stale_control`). Обычные игровые тики не меняют этот счётчик. Старые клиенты могут продолжать отправлять задачи без этого поля.

Цель создаётся только локальным владельцем; операции `model.start` по сети нет. Для её действий передаётся `model_goal_id`. Отменённая или сменившаяся цель отклоняет поздние задачи/отчёты с `stale_goal`. Статус `completed` означает сообщение модели о завершении цели; фактические игровые изменения подтверждаются обычными результатами задач.

Зависимости ссылаются на ранее принятые задачи; неуспех зависимости даёт dependency_failed. В каждый момент выполняется одна задача. Пауза освобождает управление; отмена не откатывает мир. После control.stop нужен F8 владельцем.

Открытие окна F7 временно освобождает игровые клавиши и останавливает продвижение текущей задачи без отмены цели. Задача остаётся `running` с `result.stage: owner_panel_open`; её исходные координаты/углы и подтверждённый прогресс сохраняются. После закрытия окна выполнение продолжается, короткие таймеры подтверждения/застревания переинициализируются. Исходный `deadline_tick` сохраняется: время, проведённое в F7, входит в лимит задачи. F9 внутри окна отменяет задачу и не допускает возобновления при закрытии.

Для `combat.ranged` F7 прерывает натяжение до выстрела штатным переключением hotbar туда и обратно, сохраняя выбранный слот и стопку лука/стрел. Так же прерывают натяжение F9, task.cancel, ручное вмешательство и разрыв связи. Возобновление такой задачи завершается `draw_interrupted`; отправьте новую задачу. После уже выпущенной стрелы отмена не удаляет снаряд: итог отмены содержит только receipts, полученные к моменту остановки, и не обещает добавить более позднее попадание.

События содержат event_id, sequence, game_tick, revision. Типы: task.*, actor.health/death, inventory.changed, entity.observed/observation_lost, interface.changed, observe.changed, control.*, model.updated, vision.error. Потеря наблюдения не равна смерти. Критические события здоровья, смерти, задач и новых целей доставляются без обычной подписки.

История — 512 событий. session.resume возвращает history_gap, events, snapshot, tasks, last_sequence, require_plan_revalidation. При разрыве/переполнении обновите снимок и задачи; движение не возобновляется автоматически. task.resume нужен для конкретной paused задачи. Результаты живут в текущей сессии; при лимите 256 задач терминальные записи могут освобождаться.

## Действия

Действия доступны в task.submit или непосредственно в type (со стандартными лимитами):

| Действие | Параметры |
| --- | --- |
| move.to | target: {x,y,z}, tolerance: 0.3..16, sprint: boolean, crouch: boolean |
| move.relative | forward / right: числа -16..16, по умолчанию 0; длина смещения (0,16]; tolerance: 0.3..16, sprint / crouch: boolean |
| move.follow | entity_id: UUID; distance: 0.7..16, по умолчанию 3; ticks: целое 1..1200, по умолчанию 200; sprint, crouch |
| move.jump | count: целое 1..30, по умолчанию 1; прыжки на месте |
| move.crouch | ticks: целое 1..200, по умолчанию 20; приседание на месте с последующим отпусканием |
| look.at | target или entity_id |
| look.turn | delta_yaw: число -180..180, delta_pitch: число -90..90; по умолчанию 0, хотя бы одно ненулевое |
| combat.attack | entity_id, chase, stop_health |
| combat.ranged | entity_id: обязательный UUID; charge_ticks: целое 20..60, по умолчанию 20; wait_ticks: целое 10..100, по умолчанию 40; max_distance: число 1..32, по умолчанию 24; hand: main only |
| item.drop | count: 1..64, по умолчанию 1; опционально expected_item: namespace:id |
| item.pickup | entity_id: UUID наблюдаемой сущности minecraft:item |
| item.use | hand: main/off, по умолчанию main; duration_ticks: 1..1200, по умолчанию 40; опционально target: {x,y,z} |
| world.interact / container.open | position или entity_id |
| container.close | {} |
| block.break | position, require_tool: true |
| block.place | position, block: namespace:id, properties: {} |
| inventory.select | slot: 0..8 |
| inventory.select_item | item: namespace:id, опционально hotbar_slot: 0..8 |
| inventory.transfer / equip | from_slot, to_slot, count: 1..64, menu_id, menu_revision |
| craft.execute | item, count: 1..4096 |
| build.execute | origin, rotation: 0/90/180/270, blocks, replace: false |

`combat.ranged` делает ровно один выстрел из обычного `minecraft:bow` в основной руке, без преследования. `shots`, `count` и `chase` не поддерживаются. Требуется наблюдаемая, видимая и живая неигровая цель; игроки, вода и лава не поддерживаются. Стрелы должны быть доступны по обычным правилам Minecraft. `max_distance` задаёт максимальную дистанцию до цели. `charge_ticks` задаёт требуемое серверное время натяжения `use_ticks`; `wait_ticks` ограничивает ожидание попадания после выпуска стрелы.

До первого воздействия задача резервирует бюджет двух действий — начать натяжение и отпустить лук; нужен `max_actions >= 2`. При меньшем бюджете задача отклоняется до начала натяжения. Мод сам не повторяет выстрел.

Успех `hit` или `defeated` подтверждается только событием `LivingDamageEvent.Post` для конкретной стрелы, выпущенной этим actor. Появление стрелы не доказывает попадание. При подтверждённом выпуске без события урона возвращается `hit_unconfirmed` и `confirmed_changes.shots: 1`; если сам выпуск не подтверждён — `shot_unconfirmed`. `confirmed_changes` содержит `shots`, `hits`, `damage`, `target_defeated` и `combat: {target, projectile_id, remaining_health, tick, source}`. `combat.attack` также подтверждает серверные `hits`, `damage` и поражение; `attack_requests` учитывается отдельно от попаданий. `combat.remaining_health: -1` означает неизвестное здоровье до подтверждённого попадания; это не признак смерти. Для ближней атаки `projectile_id` может отсутствовать.

`map.nearest`, `map.query` и `memory.query` принимают конечные `x`, `y`, `z`, `block` с одним точным ID либо `blocks` со списком до 16 точных ID, `radius: 1..64`, `limit: 1..128` и опциональный `max_age_ticks: 0..120000`. Запись помечается `observed` только если текущий тик совпадает с `last_seen_tick`; иначе она `remembered`. Неизвестное остаётся неизвестным и не является фактом. Подтверждённый `block.break` или `block.place` обновляет запись памяти фактическим состоянием блока.

`route.plan`, `craft.plan`, `build.plan` и `inventory.inspect` доступны через `model.query`; прежние SDK read endpoints `map.query` и `memory.query` сохранены. Для планирования через модель используйте заявленные `capabilities.queries`. `inventory.inspect` в `model.query` может ограничиваться `item`.

`inventory.select_item` ищет предмет в main inventory (`0..35`) и выбирает его в hotbar через штатный SWAP; `hotbar_slot` опционально задаёт целевой слот `0..8`. Успех подтверждается проверкой обеих ячеек и выбранного слота. Если для SWAP требуется закрытый контейнер, открытый контейнер приводит к отказу до изменения слотов. `block.place` и `build.execute` сами подготавливают необходимые материалы из инвентаря таким же способом; материал не обязан заранее находиться в hotbar.

`context.menu_slots` содержит `role`: `main`, `hotbar`, `armor`, `offhand`, `player_special`, `craft_grid`, `craft_output` или `container`. Для слотов игрока `inventory_slot` задаёт индекс в его инвентаре; команды transfer/equip всё равно принимают общий индекс `slot`. Компактный снимок выбирает пустые назначения `main`/`hotbar`/`container`; запрос `inventory.inspect` с `item` возвращает подходящие занятые ячейки и до четырёх обычных пустых назначений. Остальные предметы при фильтрации остаются неизвестными.

Операции с меню выполняются атомарными группами кликов: остаток бюджета проверяется до того, как курсор будет затронут. Перенос всей стопки требует двух кликов. Слоты относятся к текущему меню, не к индексам инвентаря игрока: используйте `context.menu_slots/menu_id/menu_revision`. Экипировка — перенос в разрешённый armor/offhand слот. Занятый курсор или недостаточная ёмкость отклоняют перенос.

XYZ — мировые координаты в блоках в текущем измерении. Блоки и чертежи целочисленные. Маршрут ограничен 96 блоками и 8192 ячейками; жидкости, опасности, неподдержанные коллизии и неизвестные чанки исключаются.

`move.relative` фиксирует абсолютную цель один раз в начале задачи: `forward` вдоль исходного горизонтального взгляда, `right` вправо от него, Y сохраняется исходным. При yaw=0 вперёд — +Z, вправо — −X. Используется обычный безопасный маршрут; это не удержание клавиши назад/вбок, и игрок может повернуться к цели. `sprint` и `crouch` по умолчанию false; одновременно true отклоняются. `move.to` также поддерживает `crouch`. Успех движения к точке требует серверной позиции в пределах допуска: результат содержит `position`, `target`, `remaining_distance`, `source: integrated_server` и `confirmed_changes.position`.

`move.follow` сопровождает наблюдаемую живую сущность обычным движением и заканчивается после `ticks` серверных тиков в пределах `distance`. Начальное приближение не засчитывается; время считается между последовательными серверными снимками, в которых обе позиции находятся в пределах дистанции. Промежутки больше десяти тиков без свежего снимка не засчитываются. После выхода за дистанцию уже накопленный прогресс сохраняется, отсчёт продолжится после приближения. F7, ручная пауза и разрыв связи сохраняют прогресс, но исключают время паузы; после разрыва требуется явное возобновление. Исчезновение из наблюдения даёт `target_lost` без вывода о смерти. Итог содержит `confirmed_follow_ticks`, `requested_ticks`, последние серверные позиции и дистанцию, `source: integrated_server`; `confirmed_changes.follow_ticks` сохраняется также при отмене или ошибке. Бюджет ограничивает новые нажатия движения; ожидание рядом с целью не расходует действия. `sprint` и `crouch` одновременно запрещены.

План маршрута исключает столкновения стоящего игрока между соседними точками, включая место для подъёма под потолком. Та же проверка повторяется перед следующим движением, если препятствие появилось после планирования. Это консервативный маршрут для стоящего персонажа; узкие проходы только для ползания и прыжки через разрывы не поддерживаются.

`look.turn` фиксирует углы относительно исходного взгляда: положительный `delta_yaw` вправо, положительный `delta_pitch` вниз. Yaw оборачивается, итоговый pitch ограничивается диапазоном −90..90. Успех требует подтверждения углов встроенным сервером; результат содержит `yaw`, `pitch`, `source: integrated_server`, а `confirmed_changes.look` — оба угла. Без подтверждения возвращается `look_unconfirmed`.

`move.crouch` отсчитывает длительность по серверным наблюдениям приседания, затем отпускает управление и ждёт серверного подтверждения отпускания. Требуется игрок на земле, вне воды/лавы, транспорта и полёта; открытый интерфейс не допускается. Результат содержит `stage: done`, `requested_ticks`, `confirmed_crouch_ticks`, `source: integrated_server` и `confirmed_changes.crouch_ticks`. Фактическое число подтверждённых тиков может на несколько тиков превышать запрошенное из-за задержки наблюдения. Ошибки: `crouch_unavailable`, `interface_open`, `crouch_unconfirmed`, `crouch_release_unconfirmed`. Ручное вмешательство, отмена и F9 отпускают управление. В снимке `actor` доступны также boolean-поля `crouching` и `sprinting`.

`move.jump` выполняет короткие нажатия клавиши прыжка и считает только пары «отрыв выше исходной высоты → приземление», подтверждённые интегрированным сервером. Запуск требует земли под игроком, отсутствия полёта, воды/лавы и транспорта. В снимке `actor` доступны `on_ground`, `flying`, `in_water`, `in_lava`, `riding`. Прогресс/результат содержит `requested`, `completed`, `jump_requests`, `stage`, `source: integrated_server`; `confirmed_changes.jumps` и `actions` отражают число подтверждённых прыжков. До подтверждения может быть только один запрос прыжка. Недостаточный бюджет действий останавливает серию перед следующим нажатием; точный бюджет позволяет дождаться последнего приземления. Отсутствие подтверждения отрыва более 20 тиков даёт `jump_unconfirmed`, неподходящий режим игрока — `jump_unavailable`. Лимит времени, разрешённые области, ручное вмешательство и F9 действуют как для других задач.

`item.drop` выбрасывает только выбранный предмет основной руки (hotbar), выполняя отдельное обычное действие выброса на каждый предмет. Уменьшение стака подтверждается встроенным сервером. `max_actions` равный `count` позволяет выполнить и подтвердить весь запрос; частичный результат содержит `confirmed_changes.drop: {item, count}` с фактически выброшенным количеством. `expected_item`, если передан, ограничивает допустимый тип предмета.

`item.pickup` принимает UUID наблюдаемой сущности `minecraft:item` и подбирает её стак обычным перемещением игрока. Успех подтверждается сервером для этого actor и точного UUID предметной сущности. Исчезновение цели само по себе успехом не считается. При нехватке места ошибка `inventory_full` сохраняет частичный результат с `collected`, `remaining` и `confirmed_changes.pickup: {item, count}`.

При полном подборе `source` равен `integrated_server_pickup_event`. При частичной вставке Minecraft может пропустить итоговое событие: тогда после серверного события столкновения сверяются уменьшение того же стака и равный прирост предметов у того же игрока в том же тике; `source: integrated_server_pickup_state`. Ни сущность, ни инвентарь этой проверкой не изменяются.

`item.use` по умолчанию удерживает использование основной руки до 40 тиков или естественного завершения. Ошибки `empty_hand` и `use_no_effect` отражают отсутствие предмета и отсутствие подтверждаемого использования/эффекта. Результат содержит `before`, `after`, `server_use_confirmed`, `effect_observed`, `source: integrated_server`; поле `outcome` указывает `held_item_changed`, `item_use_recorded` либо `use_released`. `confirmed_changes.item_use` сообщает предмет, руку, подтверждённое изменение предмета, наблюдённые серверные тики использования и прирост счётчика использования. Само изменение голода/здоровья не подтверждает использование. `target`, если указан, только направляет камеру; клик по блоку или сущности выполняется действием `world.interact`. Неизменившийся предмет не гарантирует употребление еды или попадание по цели. Кнопка отпускается перед автоматическим повтором Minecraft.

Для `item.use`, последнего `item.drop`, `inventory.select` и `container.close` точный бюджет действий позволяет дождаться подтверждения без дополнительной команды. `item.pickup` после исчерпания бюджета движения отпускает управление и ждёт событие не более 20 тиков. Исходные сроки задачи и остановка владельцем продолжают действовать.

Чертёж:

```json
{
  "origin": {"x":0,"y":64,"z":0}, "rotation":90,
  "blocks": [
    {"x":0,"y":0,"z":0,"type":"minecraft:stone"},
    {"x":1,"y":0,"z":0,"type":"minecraft:oak_log","properties":{"axis":"y"}}
  ]
}
```

Позиции относительны origin; поворачиваются координаты, facing и ось X/Z. План не меняет мир. Исполнитель проверяет реальные блоки/опоры/материал; итоговый успех требует проверки всего чертежа сервером.

## Наблюдение для модели vLLM

Windows-контроллер передаёт Colab цель, наблюдение, доступные действия, бюджеты каждой задачи и `goal_progress`. Это часть запроса к модели, не новая операция WebSocket:

```json
{
  "goal_progress": {
    "initial_actor": {"position":{"x":0,"y":64,"z":0},"yaw":0,"pitch":0},
    "completed_steps": 2,
    "confirmed_jumps": 10
  }
}
```

`initial_actor` содержит только фактические `position`, `yaw`, `pitch` первого наблюдения текущей цели и сохраняется до её завершения. `completed_steps` считает успешные задачи с уникальными `task_id`; `confirmed_jumps` суммирует их серверные `confirmed_changes.jumps`, включая подтверждённую часть неуспешной задачи, без повторного подсчёта одного ID. Модель использует накопленный счётчик, чтобы не повторять уже выполненные прыжки, а исходный взгляд — чтобы понимать направления цели после предыдущего поворота.

В компактном запросе `recent_results` содержит только последний сокращённый результат. Контроллер сохраняет полную историю `{decision, result}` текущей цели в памяти и рассчитывает `goal_progress` по всей истории. Сокращение запроса не меняет результат задачи мода и не обнуляет подтверждённый прогресс.

При наличии подтверждений предметных действий `goal_progress` включает `dropped_items` и `picked_up_items`: суммы `{namespace:item: count}` по всей цели, включая частичные результаты отменённых/неуспешных задач. Повтор одного `task_id` не учитывается второй раз.

## Зрение MBV1

```
4 bytes "MBV1"
uint32 big-endian: размер JSON
UTF-8 JSON metadata
rgb.bytes: PNG
depth.bytes: float32 little-endian
```

Порядок пикселей: слева направо, сверху вниз. Глубина — расстояние вдоль оси камеры в блоках; фон/невалидные значения — NaN. Проекция column-major. crop задан в исходных пикселях framebuffer от верхнего левого угла: x,y,width,height.

Метаданные: frame_id, observation_id, actor_id, dimension, capture_time, game_tick, world_revision, camera, rgb, depth, objects, observation, sync_quality, age_ms_at_enqueue, limitations, request_id. RGB/depth — один framebuffer; геометрия сущностей относится к тику, рендер интерполирован. Это явно обозначено. Прозрачность, частицы, дрожание камеры, шейдеры/постэффекты могут нарушать выравнивание.

Прямоугольник сущности — не маска. Включение в objects требует луча и согласованности глубины у центра; visible_fraction=unknown. Блоки имеют пиксель поверхности и грань. Нативный захват поддерживает OpenGL и исходный framebuffer ≤8 мегапикселей.

В потоке сохраняется последний кадр; команды/результаты передаются раньше изображения. Переполнение управляющей очереди закрывает соединение с причиной и требует resume. Входное сообщение ограничено 64 KiB.
