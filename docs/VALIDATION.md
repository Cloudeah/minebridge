# Проверки реализации 0.15.0

Проверено в облачной среде **Linux x86_64, JDK 25, Minecraft 26.1.2, NeoForge 26.1.2.97**. Игровые сценарии выполнялись через Python SDK в настоящем клиенте Minecraft через NeoForge dev-loader, в одиночном мире `BridgeSmoke`, под Xvfb с Mesa llvmpipe. Это проверка поведения, а не измерение производительности компьютера пользователя.

## Автоматические проверки

```bash
python scripts/dev.py :core:test :mod:build
.venv/bin/python -m unittest discover -s python -p 'test_*.py'
```

Сборка успешна: **230 Java-тестов**, без ошибок и пропусков. Python-набор: **98 тестов**, все прошли. После изменения транспортного сценария отдельно повторно прошла передача повёрнутого чертежа кровати с головой первой через notebook, HTTP relay и защищённую задачу.

В 0.15.0 добавлены 17 Java-проверок группировки составных блоков, стоимости одной установки, неявных частей, порядка, всех четырёх поворотов кровати, согласованности свойств, пересечений, неизвестных механик, границ координат и лимита 4096 после расширения. Python проверяет новый признак поддержки строительства и не предлагает новый контракт старому моду.

Проверки охватывают авторизацию и права владельца, фильтрацию capabilities, состояние задач/целей, отмену и запоздалые решения, дедупликацию, сроки/бюджеты, компактные наблюдения, память, планировщики и формат MBV1. В 0.14.0 добавлены проверки происхождения установки, точного клика/руки/материала, отдельных клеток многоблочного события, окончательной отмены, чужих/неоднозначных/запоздалых событий и паузы; появление блока без нужных событий не подтверждается. Python проверяет признаки поддержки, параметры размещения в обоих валидаторах, передачу установки/чертежа через notebook и relay, частичные счётчики и единственную копию receipt. В 0.13.0 добавлены проверки единственного неподтверждённого шага крафта, смены меню, тайм-аута и паузы без повторной отправки, старых образцов и параметров станции. Python проверяет одинаковую валидацию крафта и планирования в notebook/контроллере и передачу выбора станции через HTTP relay в защищённую задачу. В 0.12.0 добавлены проверки отдельного подтверждения каждого удара, ограниченного числа попаданий, раннего поражения, паузы/тайм-аута без повтора, границ погони и параметров. Capabilities проверяют фильтрацию признаков по доступным действиям владельца; Python не предлагает новый бой старому моду без признака поддержки и передаёт параметры без изменения через notebook/relay. В 0.11.0 добавлены проверки выбора пригодного инструмента, точного экземпляра, происхождения события добычи, неоднозначных/чужих/отменённых/запоздалых событий, внешнего удаления, пауз и замены блока жидкостью. Python проверяет параметры добычи, передачу через notebook/relay и отдельный счётчик добычи без выдуманного подбора. В 0.10.0 добавлены проверки перестановок через занятый и пустой буфер, точных стопок одного типа, кратких счётчиков F7, согласованности валидаторов notebook/контроллера, сохранения исходной ячейки в отфильтрованном query и сохранения ячеек экипировки при сокращении контекста. В 0.9.0 добавлены проверки серверных событий взаимодействий, конкретной цели/руки/актёра, отказов неоднозначным или запоздалым подтверждениям, сохранения факта после паузы и приоритетов компактного наблюдения. В 0.8.0 добавлены проверки цикла арбалета, рассогласования клиентской/серверной зарядки, запрета автоматического повтора, сохранения загрузки после прерывания, неподдержанных снарядов и передачи решения через notebook/relay. В 0.7.0 добавлены проверки серверного времени сопровождения, исключения пауз, потери дистанции, устаревших/редких снимков, бюджета и свободного пространства переходов. В 0.6.0 добавлены проверки происхождения серверного урона, конкретного UUID стрелы, временных окон отдельного удара, изоляции актёров/целей/измерений, запрета повторного выпуска, ручных ударов на паузе и атомарного сохранения терминального результата. Защищённые queries, память ресурсов и предварительные бюджеты кликов из 0.5.0 остаются в наборе.

Python-интеграция использует настоящий локальный HTTP/WebSocket и код функций опубликованного notebook с фиксированными ответами тестового API. Проверены передача решений/PNG, токены relay, Colab Secrets с ручным резервным вводом, лимиты контекста/времени/действий, повтор генерации неверного JSON, повтор доставки того же результата и отказ истёкшему заданию. Новые сценарии проверяют запрос плана перед действием, две последовательные цели владельца и сокращение слишком большого наблюдения через `/tokenize` с сохранением цели и подтверждённого прогресса. Дополнительно проверены пути решений `block.place` и `build.execute`, `combat.attack` с числом попаданий и радиусом погони, `block.break` с политиками инструмента, `inventory.equip` с именованным местом и `inventory.swap`, а также `world.interact` (включая вторую руку), `combat.ranged` и `move.follow` через notebook, HTTP-relay и защищённую WebSocket-задачу с неизменными параметрами, целями и лимитами. Тестовый API не запускает нейросеть.

Официальные tokenizer и chat template Gemma 4 E2B проверены на CPU на **3424 вариантах текстовых запросов** для 0.15.0: исходная цель, фактические планы и результаты многоблочного размещения, частичного строительства и цепочек крафта, ограниченного боя, погони, добычи, остановки, размещения, экипировки, переноса, взаимодействий, прерываний, лука, арбалета и сопровождения, повтор генерации, обычный и полный инвентарь из 36 слотов, заряженный арбалет и наблюдение с четырьмя предметными сущностями. Объявлены 24 игровых действия и `query` с семью операциями. Исходный максимум — **3541 входной токен**. После автоматического сокращения наблюдений максимум вместе с резервом 256 токенов ответа — **3072 из 3072**, потребовалось не более шести сокращений. Проверено сохранение цели, подтверждённого прогресса, недавних результатов и наблюдённых ячеек экипировки при сокращении. Дублированное подтверждение размещения, добычи, взаимодействия, перестановки или переноса передаётся модели один раз. В размещении основная клетка сохраняется как position/before/after, другие клетки передаются отдельно с общим числом изменённых клеток; внутренний receipt_id остаётся только в полном API. Исходные API-результаты не изменяются. Для исполненного крафта модель получает счётчик этапов и последний подтверждённый рецепт без дублированной цепочки; полный результат API сохраняется. При дальнейшем сокращении контекста недавний план и подтверждения остаются неизменными. Это измерение конкретных запросов, а не сравнение расхода токенов с предыдущей версией; перед каждой генерацией notebook проверяет фактическую длину через `/tokenize` и прекращает запрос, если обязательные данные не помещаются.

Факт выпуска принимается только для новой серверной стрелы и её первого игрового тика; загрузка старой стрелы из сохранения не считается новым выстрелом. Попадание учитывается по `LivingDamageEvent.Post` от конкретного снаряда владельца. Временные окна receipts используют серверный тик из подтверждающего снимка, поскольку клиентский счётчик может опережать сервер. Отмена после выпуска не удаляет стрелу; терминальный результат фиксирует только receipts, полученные к его атомарной фиксации.

Исчезновение сущности само по себе не подтверждает подбор.
